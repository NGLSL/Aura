# 浏览器环境配置与检测

Status: resolved
Category: enhancement
Date: 2026-10-15
Source: [GitHub #1](https://github.com/NGLSL/Aura/issues/1)

## 问题陈述

用户希望根据网络出口 IP 获取合适的时区，确认通过 Aura 启动的 Chrome 在界面退出后仍能正常使用，并方便地打开第三方检测页面。用户还希望不同 Chrome 用户配置能够使用不同的 Aura 环境，且环境配置界面的国家和地区名称统一显示为中文。

当前存在以下差距：

- 时区需要手动填写；Aura 自己的出口、Chrome 出口和 Claude 分流出口可能不同。
- Windows 时区与 IANA 时区同时存在，现有常见配对表不足以覆盖 IP 查询可能返回的全部时区。
- Chrome 的不同用户配置可能共用同一个浏览器根进程，仅选择不同 `profile-directory` 不足以获得独立 Aura 环境。
- 已有独立会话后台支持界面退出后继续运行，但缺少本次 Chrome 场景的实际验收。
- 检测站需要用户自行打开，容易在系统默认浏览器或错误的环境中进行检测。
- 地区下拉框只有中国、美国显示中文，其余已支持选项显示代码，卡片和详情也存在直接显示地区代码的情况。

## 解决方案

交付以下能力：

1. **检测真实出口并填入时区**：在 Environment Profile 编辑器中通过该草稿的网络路径检测出口 IP；IP 只读，展示具体时区结果，确认后填入 Windows 与 IANA 字段，再保存。
2. **Chrome 独立数据目录**：Application 提供可选的独立浏览器数据目录开关，按应用和本次选中的 Profile 稳定分配目录，支持不同环境并存。Host 使用独立身份。普通运行与环境工作区使用相同目录规则。
3. **两个检测入口**：使用选中的 Chrome Application 及运行环境，打开 [IPPure Claude 检测页](https://ippure.com/claude.html)或 [Net.Coffee Claude 检测页](https://ip.net.coffee/claude/)。首版在浏览器中查看检测结果。
4. **地区名称中文化**：当前全部受支持的国家和地区统一使用中文显示，搜索同时识别中文名称与 ISO 地区代码，持久化值保持原协议标识。
5. **Profile 代理**：为 Chrome 与出口检测共同配置 HTTP／SOCKS5 代理；不修改 Windows 全局代理，不代理其他应用的全部流量。

关闭 Aura 界面后，已启动的 RuntimeInstance 仍须正常运行和创建后继进程。这是已有契约，本规格要求回归验收，不新增一套生命周期架构。

每次启动自动联网检测时区、自动提取 Chrome 代理配置及第三方评分汇总不属于首版。后续启动自动化必须先完成出口查询，再生成不可变启动配置；运行中不热更新 Profile。

## 实现决策

### 1. 时区查询与编辑流程

- 查询入口位于 Profile 编辑器的时区区域。出口 IP 只能来自本次实际请求的响应，不提供可编辑 IP 或“指定出口 IP”入口，不保存手填地址。
- 固定使用 IPPure 的 `https://my.ippure.com/v1/info` 检测实际出口并获得具体时区；Net.Coffee 浏览器检测页保留，不再调用其任意 IP 查询接口。
- 已配置 Profile 代理时，通过查询开始时捕获的当前草稿代理发送请求；未配置时沿用 Aura 当前网络并说明它不代表 Chrome 扩展或网站分流的出口。
- 每次查询返回临时结果：实际网络来源、UTC 查询时间、检测得到的 IP、服务可提供的国家/城市、原始 IANA、Windows 映射及状态。IP 以只读结果展示；响应缺少有效 IP 时查询失败。
- 只接受响应中的具体 `timezone`，保留它的 IANA 标识并校验映射。国家代表时区、城市名称推测、UTC 偏移均不能替代缺失的具体时区。
- 成功后展示预览与“填入时区”。该操作只修改当前草稿的两个时区字段；既有“保存”负责持久化。预览、取消和失败均不修改已保存 Profile。
- 草稿标识、代理模式/服务器/端口、当前时区或编辑会话变化后，先前请求结果失效；后返回的旧请求不能更新预览或填入其他草稿。关闭预览或取消编辑也使请求失效。
- 网络操作在 GUI 更新线程之外执行；每次操作总时限 10 秒、响应体上限 1 MiB，使用 HTTPS 和正常证书校验。当前请求等待期间不重复派发同一查询。
- 首版每次由用户点击触发，不进行启动后台轮询、自动重试或供应商切换。接口错误、超时、无具体时区、映射失败分别显示原因；普通应用启动不依赖检测服务在线。
- 查询 API 和检测站均按可变第三方数据处理，不作为永久稳定契约。

#### 2026-10-16 用户确认：Chrome 与出口检测共用 Profile 代理

- Profile 支持不配置代理、HTTP、SOCKS5。代理端点由协议、服务器地址和端口组成，支持域名及 IPv4/IPv6，拒绝无效端口、凭据、路径和控制字符。本轮不增加认证代理凭据、转发器或浏览器扩展。
- 不配置代理是旧配置默认值，保留原 Chrome 系统/手填代理行为；此时查询展示 Aura 当前网络来源，不声称能读取浏览器扩展或 Claude 分流规则。
- 配置代理后，普通 Run、Run With、Workspace 的 Chrome 与当前草稿查询共用同一端点。HTTP 支持 HTTPS CONNECT，SOCKS5 使用代理侧 DNS；请求失败不得改用直连。Host 启动不使用 Profile 代理。
- Profile 代理与应用手填代理控制参数冲突时明确拒绝；未配置 Profile 代理的旧应用不受新增参数前置条件约束。
- 代理随 Profile 保存并进入不可变实例快照及有效启动配置核对；代理变更后不能复用旧配置的浏览器。运行中的实例不热更新。
- 只作用于受支持 Chrome 的浏览器网络及 Aura 出口/时区检测，不改系统代理，不提供任意进程网络劫持，不保证 UDP/WebRTC 全流量代理。

### 2. 时区映射

- 继续使用现有 TimezoneProfile 的 Windows/IANA 双字段及宿主 Windows 时区存在性校验。
- 用固定版本的 Unicode CLDR Windows Zones 数据补全映射，包含其引用时区所需的别名处理；数据随产品更新，不在每次查询时下载映射。
- IANA 转 Windows 优先匹配返回的具体时区及其规范别名，不把 Windows 默认 IANA 城市反向覆盖到用户收到的具体 IANA 时区。
- 国家代码仅用于有依据的地区匹配，不得通过国家代码凭空构造时区。没有唯一、有效的 Windows 对应项时允许查看结果，禁止自动填入，交由用户手动选择。
- 自动填入同时更新两个字段；人工选择仍沿用既有编辑和保存语义。

### 3. Chrome 数据目录与启动参数

- 独立数据目录是 **Application 的启动偏好**，不是修改 Profile 的身份字段，也不代表文件系统隔离。首版作用于经现有浏览器分类确认为 Chrome 的 Win32 Executable Application。
- 老配置默认关闭，继续保持用户原有目录参数和启动行为。新增持久化字段缺失时按关闭读取；非受支持目标不得启用该偏好。
- 开启后，实际目录位于 Aura 用户数据区，以 Application UUID 和本次有效 Profile UUID 稳定分配；Host 使用单独固定身份。名称修改不换目录，Profile 删除或替换不把其他 Profile 的目录接管过来。
- 同一 Application 与 Profile 经普通 Run、Run With、环境工作区启动得到相同目录。Container 提供本次 Profile 来源，不再额外按 Container 生成第二套目录。
- 目录偏好在共享根进程启动参数合成处执行，普通 Launcher 与 Workspace/Supervisor 共同使用；只在 GUI 拼参数不符合要求。
- 开启自动目录且应用参数已有 `--user-data-dir` 时拒绝此次启动并说明冲突；用户移除手填参数或关闭开关后再启动。已有 `--profile-directory` 保留，它选择独立数据根下的子 Profile。
- 默认不会复制或迁移宿主 Chrome 的 Cookie、书签和登录信息；独立目录初次使用表现为新的浏览器数据。关闭开关、删除 Application/Profile 或退出 Aura 均不自动删除浏览器目录。
- 同目录被已有 Chrome 占用时，普通“新实例启动”应说明复用风险并拒绝把命令行转交误报为新的受控 RuntimeInstance；提示用户关闭对应浏览器后重启，不强杀浏览器。
- 普通 Run 与 Workspace 并发请求同一目录时，最多一个请求可创建新的受控浏览器，其余明确失败。占用判定须覆盖启动竞态及实际根进程结果，不能仅依赖启动前的一次进程扫描；Aura 重启或失去原实例记录后也不得据目录路径推断受控归属。
- 检测用途允许向 **已确认属于当前 Application、本次 Profile 或 Host 身份和有效启动配置** 的浏览器打开新标签页，不能据进程名或新启动进程的注入成功就认定旧窗口被正确控制。无法确认同目录已有浏览器归属或配置时，提示先关闭对应浏览器。
- 有效启动配置按实际 Profile 内容、浏览器参数、工作目录及影响进程树的策略核对，包括子进程继承偏好；仅比较 Profile UUID 不足以复用。普通 Run 与 Workspace 的记录格式不同不代表配置不同，也不能掩盖实际继承策略等差异。Host 不要求 Runtime 载入证据，但仍须核对应用、Host 身份、实际浏览器目录及参数。
- Profile 改动不热更新已打开的 Chrome；检测已运行实例时明确使用它的启动配置。要验收最新保存配置，必须关闭对应浏览器再启动。
- GUI 与 Workspace 的检测用途使用相同规则。原始 CLI 直接运行命令没有持久 Application 身份，保持显式参数语义，不给 nil 身份隐式分配公共目录。

#### 2026-10-16 用户确认：Chrome 工作区兼容启动

实际 Chrome 含 TLS 初始化回调，被既有 Workspace 入口门禁拒绝（0xC0000142）；普通应用入口不受该门禁影响。用户确认仅对受支持 Chrome 的 Workspace 运行采用启动前明确选择的兼容模式：

- 仍强制注入并确认根进程的实际 Runtime、Profile/配置、进程身份和 Job 归属；注入失败仍拒绝启动。
- 运行记录和界面使用独立的兼容启动保证，不声称通过严格入口门禁；其他应用保持原有门禁。
- Job 成员列表记录真实进程；仅实际认证的成员记录 Runtime 证据。Chrome 沙箱子进程未认证时不能当作已注入，网页/系统接口读值仍以实际观察为准。
- 关闭 GUI 不影响继续使用。Supervisor 重启后不能重新确认兼容实例时标为 TrackingLost，不自动认领旧浏览器，也不因记录存在就解除目录占用。

这是用户批准的 Chrome 启动保证调整；不改变 Profile 不可变、目录冲突拒绝或 Host 不注入语义。

### 4. 两个检测入口

- 仅提供 IPPure Claude 检测和 Net.Coffee Claude 检测两个固定入口，不新增供应商列表或自定义 URL 设置。
- 入口绑定选中的 Chrome Application 与运行环境。默认 Profile、Run With、本次 Workspace Profile 和明确选择的 Host 均可作为上下文，界面显示实际采用的环境。
- 通过同一应用的启动链路打开页面，保留工作目录、已保存参数、浏览器目录和环境策略。检测 URL 作为本次受限启动意图传递，不写回 Application.arguments。
- 不通过系统默认浏览器关联打开，也不借用 Aura 内嵌网页替代目标 Chrome。Workspace 检测意图通过既有 Supervisor 控制链路传递，服务端只接收两个固定站点枚举，不开放任意远程 URL 注入。
- 首版由网页显示检测结果；Aura 不抓取完整评分，不自动采集字体、Canvas 或设备信息，不根据分数调整配置。
- 页面无法访问时保留浏览器和实例。用户可重试或继续正常使用；网站评分不是 Aura 启动成功的判据，也不是 Anthropic 的官方风控结论。

### 6. 退出与运行契约

- 退出或终止 Aura 界面进程后，经 Profile 启动的 Chrome 及其受控进程树继续运行；独立 session host/Broker 随目标进程树存活。Host 模式不注入 Runtime，要求界面退出后继续正常使用并保持宿主环境。
- 保留既有注入失败拒绝启动、子进程 Profile 继承和显式停止语义。检测请求或页面不能成为后台会话必须持续依赖的资源。
- 验收以真正退出界面后的浏览器操作和进程/Runtime 证据为准，最小化到托盘不等同退出。强制结束所有会话后台进程不属于正常界面退出。

### 7. 页面分工（2026-10-16 用户确认）

- **环境配置页**只负责查看和编辑 Profile，包括出口／时区查询与代理设置；不提供应用选择、应用启动、浏览器检测或实例管理面板。查看或切换 Profile 不应为展示配置而连接 Supervisor。
- **应用页**负责选择应用及运行环境，保留默认启动、临时选择 Profile、Host 和两个固定浏览器检测入口。普通启动继续使用原有启动链路，不因为移除 Profile 面板而新增 Supervisor 可用性等前置条件。
- **运行实例页**集中展示本次界面管理的实例及 Supervisor 管理的实例，提供刷新、停止、诊断和未知启动结果查询。应用筛选同时适用于两类记录，不重复显示同一实例。
- Supervisor 实例管理以运行记录中的 Application、Profile、Container、Instance 和 generation 为准，不依赖环境配置页当前选中的草稿。已删除的应用或 Profile 不应使原实例失去查看和管理入口；TrackingLost、服务换代及停止作用域的安全限制保持不变。
- 后端 Workspace/Container 协议及历史记录继续兼容，不再以 Profile 页启动面板作为用户入口。此前将 `run_panel` 接入 Profile 概览是界面分工偏差，本次撤除；GitHub #1 没有要求该面板。

## 验证决策

遵守当前项目规则：**禁止编写测试用例**。实现后复用已有构建、静态检查、Probe、Browser Probe 和 detached-session 检查，结合人工浏览器操作取证；以下是验收条件，不要求编写测试文件或脚本。

主要验证入口是“已保存 Chrome Application + 已保存 Profile → 启动 → 在同一浏览器中检测与继续操作”。源码检查、实际浏览器结果和第三方站点评分分别记录，不能互相替代。

## 不在首版范围

- 每次启动自动检测并改写有效时区；后台定时检测或运行中热更新。
- 自动读取 Chrome 扩展、PAC、TUN 或分流规则；通过 CDP 接管用户现有浏览器；修改宿主全局代理。
- 第三方检测报告聚合、风险评分门槛、字体/Canvas/GPU 指纹虚拟化、反检测或账户风控承诺。
- 自动迁移、复制或删除宿主浏览器数据，强制结束已有 Chrome。
- 为任意 CLI 命令、Electron、WebView2 或 Packaged 目标自动管理数据目录；新增 CLI 检测命令。
- 扩展全球国家/地区列表，翻译用户自定义 Profile/Application 名称或改写协议标识。
- 新增 Runtime Hook、修改全局时区或网络设置、驱动或安全隔离。
