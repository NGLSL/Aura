# Aura v0.3.13

This release fixes Runtime timezone caching and ANSI child-process startup defects, applies Profile language settings to Chrome/Edge sandboxed renderers, and adds actionable child-process creation error details.

## Changes

- Chrome/Edge sandboxed renderers in Compatibility mode now receive the immutable parent's Profile environment and language arguments, even when Chromium supplies its own environment block. Browser detection also handles a null application name by parsing the command line. The browser's restricted token, sandbox startup attributes, and requested suspension state remain intact.
- Timezone lookup cache access is synchronized. Successful lookups and definitive missing timezone IDs remain cached, while temporary Windows enumeration errors are retried on later calls instead of permanently forcing that process back to the host timezone.
- Standard-time/daylight-time status is calculated using the current real UTC time rather than cached for the lifetime of the process. The expensive timezone rule lookup remains cached.
- The `CreateProcessA` Hook preserves extended startup attributes when translating `STARTUPINFOEXA` to Unicode, together with desktop, title, reserved data, and standard handles. Invalid startup structures and failed string conversions return errors instead of silently dropping startup information.
- Audit records include the child PID after successful sandboxed-renderer creation and the Windows error code after a failed creation. Other child injection failures also include their Windows error code. Command bodies and environment blocks are not added to these records.

## Validation

- Before the version bump, both x64 and x86 Runtime products compiled successfully. The existing native Profile contract check passed, and an existing parent/child Probe run exited with code 0; both processes loaded the Runtime and reported the Profile's `en-US` locale and Pacific timezone. No test cases were added or modified.
- A fresh, sandbox-enabled Chrome `154.0.8037.98` instance using a separate browser data directory reported `America/Los_Angeles`, `en-US`, and navigator languages `["en-US", "en"]`. The loaded Runtime DLL's SHA-256 matched the current build, and renderer PIDs matched the new audit records. The host retained `China Standard Time` and `zh-CN`.
- After versioning, `cargo check --workspace --locked` and `cargo build --workspace --locked` passed. Both Runtime architectures were reconfigured and rebuilt with version `0.3.13`, and the Windows application binary reports file version `0.3.13`. The separate CPU-renderer suite passed all five existing checks. These local checks do not establish installed-upgrade behavior or successful validation on another machine.
- The versioned workspace suite passed with 485 checks passed, zero failures, and 33 conditionally ignored checks. No new test cases were authored or existing test cases changed.

## Limitations

The original report of a restarted Chrome retaining host language/timezone values has not been reproduced locally. The renderer configuration change closes a verified propagation gap, but does not prove that it resolves that remote report. Sandboxed renderers still have partial native environment coverage and do not receive Runtime DLL injection through this compatibility path.

A separate `CreateProcessW` injection attempt returned `ERROR_ACCESS_DENIED` (5) during local Chrome validation. The same failure category was present in the previous version while webpage locale/timezone checks passed. The specific target of that request has not been identified, and this release does not claim to fix that access failure. Injection failures continue to reject startup.

## Upgrade

After upgrading, launch a new target application instance to load the new Runtime. Existing instances retain their startup Profile and loaded Runtime. Saved applications and Profiles do not need to be recreated.
